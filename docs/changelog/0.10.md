# 0.10 release notes

Release dates and draft status are recorded in the [root ledger](../../CHANGELOG.md).

## 0.10.1

When pathname publication observes a missing parent directory but another creator
wins `mkdir`, synchronize the admitted directory and its parent link through the
same routine used after our own successful creation. A competing creator may
stop before syncing; publication must establish those barriers independently
([#43](https://github.com/dragginzgame/ic-host-tooling/issues/43)).

Failures at either barrier remain `BeforePublication` and prevent staging or
final output creation. Existing parent directories and existing lock-file opens
retain their current behavior. No API, storage-format or consumer migration
change is required beyond the 0.10.0 contract. Regression coverage exercises the
creation race, both sync barriers and their original I/O failures.

Correct the cleanup assertions to detect the current `.ic-host-tmp-` staging
names, so retained temporary files cannot pass checks using the retired prefix.

## 0.10.0

### Breaking: one pathname writer and publication error contract

`durable::write_with(path, options, producer)` replaces both the old two-argument
I/O-only writer and `write_typed_with`. It takes explicit `WriteOptions`, supports
typed producer errors and returns `Result<T, NamedWriteError<E>>`. There is no
compatibility alias for the removed name. The named, closed-writer validation
and descriptor-relative entrypoints retain their distinct contracts.

For an old replacement call, pass the previous defaults explicitly:

```rust
use ic_host_fs::durable::{PublicationMode, WriteOptions, write_with};
use std::{io, path::Path};

fn copy_to(path: &Path, input: &mut impl io::Read)
    -> Result<u64, ic_host_fs::durable::NamedWriteError<io::Error>>
{
    write_with(path, WriteOptions {
        mode: PublicationMode::Replace,
        permissions: 0o666,
    }, |file| io::copy(input, file))
}
```

Existing three-argument `write_typed_with` calls only need the name changed.
Producer closures using `?` and an otherwise untyped `Ok` may need an explicit
return type such as `-> io::Result<_>`.

`write_bytes`, `create_new_bytes_with_parents` and
`create_private_bytes_with_parents` now return
`Result<(), NamedWriteError<io::Error>>`. Their replacement/create-only modes,
permissions, parent creation and byte formats are unchanged. All publication
entrypoints retain:

- `Producer { source, cleanup_error }`: production failed without publication.
- `BeforePublication { source, cleanup_error }`: a filesystem operation failed
  before publication; owned staging removal may also have failed.
- `AfterPublication { source }`: the new output is visible, but staging cleanup
  or final directory synchronization failed. Reconcile before retrying.

Callers that previously used `.kind()` must first match the phase. A create-only
`AlreadyExists` recovery branch should match `BeforePublication` and retain any
cleanup error; it must not treat an after-publication error as safe to retry.
Preserve the whole typed error in domain errors or an explicit I/O wrapper;
extracting only `source` loses publication and cleanup evidence.

`RegularFileLockError` adds `Publication(NamedWriteError<io::Error>)` for durable
lock-file creation. Update exhaustive matches. Existing-file admission and lock
syscalls still use their prior categories, including native contention errors.
Conversion into `io::Error` wraps the entire publication variant with kind
`Other`, so consumers can downcast it without losing evidence. A missing-lock
creation race is accepted only for before-publication `AlreadyExists` with
successful staging cleanup.

Remove the private `NamedWriteError::into_io` and
`supported::commit_with_writer_and_hook` adapters that discarded error state.
The byte fault-injection helper is test-only. Fault tests now assert publication
phases, original producer errors and separate cleanup failures, including final
sync failures for replacement, ordinary create-only and private create-only modes.

This changes the Rust API and error handling, not storage formats. There is no
retained-data migration or reset. Consumer pins, retries and paid-operation
recovery remain consumer-owned; dependency adoption requires consumer checks.
