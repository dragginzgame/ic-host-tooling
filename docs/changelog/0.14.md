# 0.14 release notes

## [0.14.2]

Adopt Shared Tooling 0.6.4 `6fc8eb9a94f83fb0b9d0a26377d4232508cdbe2d`
and its [common Make entrypoint](../make-interface.md), replacing the separate
includes and local hook/snapshot-check recipes. Existing setup, formatting,
hook and release commands keep their behavior. Host retains its ordered pinned
release-tool extension, validation gates, metadata adapter and publication policy
([Shared #130](https://github.com/dragginzgame/shared-tooling/issues/130)).

This compatible contributor-tooling update changes no crate API, dependency,
MSRV or tool pin. Existing verified tools need no reinstall. Isolated hook and
release routing checks now include the complete common entrypoint.

The README now keeps a short current setup recipe and links to the existing
[host qualification](../hosts.md) and [release/publication](../publishing.md)
guides. Host-specific release-tool and delivery details live with that procedure;
shared installation and recovery contracts remain linked to their canonical
guides ([#68](https://github.com/dragginzgame/ic-host-tooling/issues/68)).

## [0.14.1]

Adopt Shared Tooling 0.6.3 `4fd979d13c32adb3cb2f51f213ebfc4f98339b3d`.
A normal direct release command can supersede an interrupted `prepare` intent
after a clean descendant commit records the metadata's disposition. The runner
preserves the original plan, selects the requested increment from current
metadata and repeats preflight and full validation. Unchanged-HEAD preparation,
explicit resume, staged/later phases and PR delivery keep their exact recovery
contracts ([Shared #126](https://github.com/dragginzgame/shared-tooling/issues/126)).
See the [restart procedure](../releases.md#source-changes-after-saved-preparation-intent).

Host now archives existing per-version validation receipts, saved notes and logs
into a unique `release-state/X.Y.Z.validation-attempt.*` directory before fresh
validation can append or replace them. Copies are checked byte-for-byte; unsafe
entries or failed preservation stop validation while retaining existing evidence.
Successful revalidation binds the active receipt to the new source, while a
failed gate preserves the prior active receipt and notes
([#67](https://github.com/dragginzgame/ic-host-tooling/issues/67)).
Preparation remains local metadata only; no recovery helper publishes or deploys.
The Shared maintenance rules also clarify delivered-adoption issue reconciliation
against exact revisions and required native checks.

This is a compatible tooling update. Crate APIs, dependencies, pins and MSRV are
unchanged; existing verified 0.6.1 tool installations need no reinstall.

## [0.14.0]

### Completed process results and fallible observation

`capture_command`, `capture_group_command`, `communicate_child`,
`communicate_child_with_observer` and `AdmittedTool::run` return
`CompletedExecution`. Its `status` is an `ExitStatus`, including nonzero and
signalled exits. Execution failures still carry `ExecutionEvidence` with an
optional status, retained output, truncation flags and separate cleanup errors
([#66](https://github.com/dragginzgame/ic-host-tooling/issues/66)).

Call `require_success()` when a consumer requires zero exit. Nonzero completion
alone is no longer an error from the execution entry points. In particular,
external-producer publication callbacks must check success before admitting or
publishing their output. `require_complete()` now belongs to `CompletedExecution`
and still rejects either truncated stream. Both checks retain the original status
and bytes on rejection without copying buffers or performing child cleanup.
`From<CompletedExecution> for ExecutionEvidence` supports failure projections.

Version admission, Git provenance and Candid extraction explicitly require both
success and complete output before interpretation. Their completed evidence
fields now use `CompletedExecution`; failure evidence remains optional-status.
Consumers exposing these public types must migrate their own public contracts.

For a capture caller that previously recovered nonzero results from
`ToolError::Execution`:

```rust,ignore
let output = capture_command(&mut command, limits)?.require_complete()?;
if output.status.success() {
    // Interpret successful complete output.
} else {
    // Project the completed status and diagnostics into the caller's error.
}
```

For a strict producer or probe:

```rust,ignore
let output = tool.run(&arguments, &context, limits)?
    .require_success()?
    .require_complete()?;
```

The existing output observer now returns `io::Result<()>`. Infallible event
observers finish with `Ok(())`; terminal/file forwarding can directly return
`writer.write_all(bytes)`. The first rejected chunk stops observation and closes
pipes through the existing cleanup path. `ExecutionFailure::Observer` identifies
the stream and preserves the original sink error, alongside retained output,
observed status and secondary cleanup errors. The error source exposes the sink
cause; default diagnostics continue to omit output and credentials.

A chunk is retained and truncation recorded before observation. If a sink rejects
the same chunk that exceeds a hard output bound, the observer failure takes
precedence and the truncation flag remains set. Panics still attempt cleanup and
resume unwinding. There is no second IO engine, retry policy or observer thread.

Ordinary nonzero/signalled leaders still undergo cleanup and reaping even with
`SuccessfulExit::Retain`; they cannot be handed off. Successful retained leaders
continue to require the caller's explicit disposition after output admission.
Cleanup failure remains an error. Output limits and optional deadlines retain
their contracts, including unlimited-duration builds with `timeout: None`.

### Shared Tooling adoption

Adopt Shared Tooling 0.6.2 `7f1ca16b0dfa98021d2671017ecb7de767409b0e`.
Interrupted releases identify the saved plan, phase, versions and both source
commits when HEAD changes. The existing source guard refuses validation reuse
for another commit. The [recovery procedure](../releases.md#source-changes-after-saved-preparation-intent)
requires positive consumer-specific proof that preparation never began before
retiring an attempt ([Shared #126](https://github.com/dragginzgame/shared-tooling/issues/126)).
Host does not journal every metadata mutation; an unchanged version or missing
journal alone cannot establish that proof. Recovery remains separately authorized.

Setup guidance distinguishes Audit and standalone Machete, inherited Cargo
launcher context and failure propagation
([Shared #123](https://github.com/dragginzgame/shared-tooling/issues/123)).
The tooling adoption changes no pin or build policy; verified 0.6.1 tool
installations need no reinstall. The process API changes above determine this
batch's minor version. Dependencies and MSRV remain unchanged.
