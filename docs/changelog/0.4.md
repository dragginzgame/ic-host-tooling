# 0.4 release notes

## 0.4.5 — pending

The durable publication engine now converts admitted permission bits to Darwin's
`u16` native mode type with a checked conversion. Linux retains its `u32` mode.
This repairs the library compilation failure introduced in 0.4.3 and present in
0.4.4 on both supported macOS architectures
([#18](https://github.com/dragginzgame/ic-host-tooling/issues/18)). Public permission
options remain `u32`, accepting only `0o000..=0o777`. Invalid or oversized values
still fail before parent/staging creation or producer invocation; no panic,
unchecked truncation or permission-policy change is introduced.

Consumers blocked on macOS need the repaired library version. Native execution
qualification is tracked in the [handoff](../status/current.md), separately from
the focused Linux checks. No API or dependency changes are required.

## 0.4.4 — 2026-10-07

### Gzip identities and exact representation comparison

`artifact::hash_gzip(bytes, max_compressed_bytes, max_decoded_bytes)` returns
the decoded byte count and SHA-256 without allocating a complete decoded buffer.
`hash_gzip_or_raw(bytes, max_input_bytes, max_payload_bytes)` additionally accepts
raw bytes, selecting gzip only for the exact `1f 8b` prefix. Malformed selected
gzip never falls back to raw hashing. Empty and one-byte inputs are raw. Both
are available through the existing optional `gzip` feature, with no new
dependency ([#12](https://github.com/dragginzgame/ic-host-tooling/issues/12)).

Input is a borrowed, already-resident slice with an explicit total-size budget.
Decoded or raw payload bytes have an independent budget. The decoder and the
existing bounded hashing traversal consume the payload incrementally; output
identities describe the raw payload, not compressed upload bytes. These helpers
do not validate Wasm or infer install limits. Consumers comparing an IC module
hash must retain their own Wasm admission and network policy.

`artifact::gzip_matches(bytes, expected, max_compressed_bytes)` compares the
decoded payload with a borrowed expected slice using exact byte equality. It
returns `false` for a shorter or different valid payload, and uses the expected
length as its decoded budget: a longer payload returns the existing typed
decoded-limit error. Canic's release-representation validator can replace its
`decode_gzip` allocation and subsequent equality comparison with this call,
retaining its mismatch-versus-invalid-gzip error mapping.

All gzip operations share the existing single-member admission owner. They
verify CRC and length, reject truncated input, concatenated members and trailing
bytes, and return no identity on failure. Comparison continues after a content
mismatch so a corrupt trailer cannot become an ordinary `false` result.
Existing `decode_gzip` behavior is retained. The `inspect_gzip` example now hashes
incrementally while preserving its strict gzip input and output fields.

These Rust helpers do not by themselves replace Toko's shell pipelines; a
consumer-owned CLI integration is still needed there. No existing API is removed.

## 0.4.3 — 2026-10-07

### Typed and descriptor-relative publication

`durable::write_typed_with(path, WriteOptions, producer)` streams output into
the existing durable engine while retaining the producer's error type in
`NamedWriteError<E>` ([#15](https://github.com/dragginzgame/ic-host-tooling/issues/15)).
For example, a JSON caller can use `serde_json::to_writer_pretty` through
`BoundedWriter<&mut File>` without allocating a complete encoded document or
converting `serde_json::Error` into I/O. Serialization and byte budgets remain
caller-owned; serde dependencies are used only by this crate's tests.

`WriteOptions` requires both `PublicationMode::{Replace, CreateNew}` and Unix
permission bits. Creation permissions are reduced by the process umask; `0o600`
provides owner-only staging but does not establish private parent custody. The
path entry point retains existing parent-creation semantics. Replace swaps the
final entry itself, including a symlink; create-new atomically refuses any
existing entry. Existing byte, I/O callback and named-producer APIs remain.

On Unix, `durable::write_at_with(parent.as_fd(), name, options, producer)` borrows
a standard directory descriptor and accepts one filename component
([#16](https://github.com/dragginzgame/ic-host-tooling/issues/16)). It never reopens
the parent through a pathname. Staging, cleanup, publication and directory sync
stay anchored to that descriptor if its original path is renamed or replaced.
Both new APIs use the same production engine as the existing durable writers;
neither introduces a filesystem dependency type into the public API.

Consumers retain root confinement, parent and final-target admission, schemas,
mode policy and exclusion of concurrent namespace writers. Query can pass its
admitted `cap_std::fs::Dir` through `AsFd`, retaining its no-follow traversal and
target validation while removing its temporary allocator/publication pipeline
and JSON error bridge after adoption. Any pre-serialization rule that prohibits
even creating parents on invalid input remains local. Backup consumers must
preserve their interruption/recovery evidence when replacing local barrier-based
writers; these APIs do not expose a new product lifecycle or crash-test framework.

Producer errors retain the original source and any separate cleanup error.
Before-publication errors leave the old destination intact; after-publication
errors mean the new output is visible and require reconciliation. The create-only
hard-link fallback now reports staging-unlink failure as `AfterPublication`
instead of silently succeeding. Such failures do not establish final directory
durability. Cleanup never removes an observed foreign replacement. A panic,
interruption or hostile concurrent writer can still leave effects requiring
consumer recovery.

### Shared tooling and releases

The snapshot adopts committed Shared Tooling 0.1.19 at
`a06e4719e3839b8eefcfb88ec8923aa88eb63ccc`
([#6](https://github.com/dragginzgame/ic-host-tooling/issues/6)). The tool-command
fixture normalizes its scratch directory, fixing the mismatch with Make's
physical `CURDIR` on macOS temporary paths. LOC reporting also follows the
correct symlinked tool target. Native qualification remains recorded separately
in the [handoff](../status/current.md).

Release preparation accepts horizontal heading whitespace consistently and
preserves historical bytes, including an absent final newline. Duplicate,
misplaced and already-finalized current candidates still fail admission.

The common Make include exposes optional `make install-rust-tools` and offline
`make rust-tools-check`; the installer refuses redirected installation paths.
These commands select the shared Rust tool bundle, including cargo-sort-derives
0.13.0 and candid-extractor 0.1.6. They are not prerequisites of the ordinary
aggregate setup/check targets. Existing tool pins remain unchanged and ordinary
validation does not install tools.

## 0.4.2 — 2026-10-07

### Chunk identities and copy errors

`artifact::chunk_digests(reader, chunk_bytes, max_bytes, max_chunks)` returns
ordered SHA-256 chunk digests and the complete `ArtifactIdentity` from one
bounded read traversal ([#12](https://github.com/dragginzgame/ic-host-tooling/issues/12)).
`chunk_bytes` is `NonZeroUsize`; both input bytes and retained digest count have
explicit limits. Reader fragmentation does not change chunk boundaries, exact
multiples have no extra empty chunk, and empty input has zero chunks with the
normal empty-stream identity. Allocation failures stay typed; failure returns
no partial identities. Working storage does not grow with the selected chunk
size, apart from the bounded returned digest vector.

The helper hashes precisely the supplied bytes. Uploading a gzip artifact hashes
its compressed chunks and compressed whole input; it does not produce a decoded
Wasm module hash. Canic's chunk-preparation callers can replace their repeated
whole/chunk digest collection after adoption. Chunk sizes, empty-payload policy,
request schemas, custody, upload limits and retries remain consumer-owned.

`io::Error::from(CopyError)` preserves a native input or output I/O error's kind,
OS code and custom cause ([#14](https://github.com/dragginzgame/ic-host-tooling/issues/14)).
Non-I/O input failures remain downcastable `CopyError` causes under `Other`.
Consumers can use `.map_err(io::Error::from)` in `durable::write_with` callbacks;
the old destination still survives a failed copy. Keep `CopyError` directly when
the input/output distinction is required, since projecting a native I/O error
intentionally drops that distinction. These additions need no new dependency
or feature and remove no API.

### Installed-tool version admission

`AdmittedTool::admit_version(&VersionSpec, &ExecutionContext, OutputLimits)`
admits a caller-trusted installed executable without requiring a published
binary digest ([#11](https://github.com/dragginzgame/ic-host-tooling/issues/11)).
This fits Cargo-built tools such as IcyDB's Candid extractor, whose bytes vary
with the host and build toolchain. Consumers can remove their local
`hash_file` followed by `ToolSpec` construction.

The shared admission engine hashes the file within the caller's executable-byte
budget, checks executable permissions and captures the exact version with the
existing output/deadline limits. `identity()` retains the observed size/digest;
every later `run` rejects byte or permission drift before spawning. Version and
execution failures keep their existing typed errors and bounded evidence.

An observed digest is not a published pin, and version text does not authenticate
an executable. The consumer must trust the installation before the version probe
and exclude concurrent writers to its executable and directories. Installation,
resolution, limits, environment and recovery remain caller-owned. `admit` with
`ToolSpec` still requires the caller's exact digest before any version execution;
it remains appropriate for published binaries such as Binaryen. No existing API
is removed and no dependency or feature selection changes.

## 0.4.1 — 2026-10-07

### Named external output

`ic_host_fs::durable::write_named_with` passes an owned absolute sibling path to
a consumer callback, then uses the existing durable publication engine. Tools
such as `wasm-opt -o PATH` can produce directly into that file without a second
temporary-file mechanism or a full-file copy
([#8](https://github.com/dragginzgame/ic-host-tooling/issues/8)).

The file is precreated and empty. The producer must write/truncate that inode;
tools that unlink or rename over their output are rejected. Consumers must check
bounded output content before returning success: existence alone does not prove
the tool produced anything. Executable admission, process bounds, arguments,
environment, schemas and recovery stay consumer-owned.

`NamedWriteError<E>` retains the original callback error, including `ToolError`
capture and kill/wait evidence. `Producer` and `BeforePublication` also expose
any staging cleanup error; `AfterPublication` reports a failed final directory
sync after the new output became visible. No automatic retry occurs.

Staging and parent identities are checked before publication; observed missing,
replaced, symlinked, special or multiply linked staging cannot be published.
Cleanup uses the retained parent descriptor and only removes the matching owned
entry. Foreign replacements and files moved elsewhere are preserved. Callers must
control the parent hierarchy, exclude concurrent namespace mutation and finish
all producers/writable handles before returning success. Identity checks do not
make comparison and rename atomic against hostile directory writers. Panics,
interruption and surviving descendants can retain effects requiring reconciliation.

### Shared tooling and releases

Shared Tooling 0.1.17 now owns the common setup/check recipes through
`make/tools.mk`. Both local Make and CI select the same pinned jq, yq, ripgrep
with PCRE2 and cloc inventory; CI no longer installs a separate package-manager
ripgrep. Existing checkouts explicitly run `make install-host-tools` to prepare
the expanded set. Verification remains offline and never installs missing tools.

`make cloc` reports workspace Rust runtime/test lines and test-function counts.
`make cloc-tooling` reports sibling tooling with matching shared snapshot bytes
separated from local code; select another parent with `CLOC_PARENT`. Reports do
not authorize deletion or establish runtime correctness.

Release heading selection accepts trailing spaces and tabs, preserves the
candidate's notes and historical bytes, and still rejects duplicate or misplaced
current entries. Setup consolidation and the local finalizer integration address
[#6](https://github.com/dragginzgame/ic-host-tooling/issues/6).
Existing Rust APIs and package versions are unchanged by this compatible batch.

The release adapter also accepts synchronized major/minor dependency requirements
such as `0.4`. It preserves their precision like `cargo set-version`: a patch
keeps `0.4`, while a minor update selects `0.5`. Full requirements remain full,
and package/lock versions still use all three components. Prepared and committed
payload checks retain exact source binding and reject unrelated metadata changes.

## 0.4.0 — 2026-10-07

Filesystem reads now have one owner, `ic_host_fs::read`. Durable publication and
locks remain in `ic_host_fs::durable`. This breaking cleanup addresses the reader
and error-loss findings in [#14](https://github.com/dragginzgame/ic-host-tooling/issues/14).
There are no compatibility reexports or deprecated unbounded readers. The
maintainer released this hard cut as 0.4.0.

### Consumer changes

| Previous API | Replacement |
| --- | --- |
| `durable::read_optional_regular_bytes(path)` | `read::read_optional_file_no_follow(path, maximum_bytes)`; the consumer must select a real byte budget |
| `durable::read_optional_regular_bytes_bounded(path, maximum_bytes)` | `read::read_optional_file_no_follow(path, maximum_bytes)` |
| `durable::read_regular_bytes(path, maximum_bytes)` | `read::read_file_no_follow(path, maximum_bytes)` |
| `durable::RegularFileReadError`, `durable::BoundedRegularFileReadError` | Existing `ic_host_artifacts::artifact::ArtifactError` |
| `durable::read_private_bytes::<N>(path)` | `read::read_private_bytes::<N>(path)`, now returning `Result<Option<[u8; N]>, PrivateFileReadError>` |
| `durable::lock_file(path)` | Existing `durable::lock_regular_file_with_parents(path)` |
| `durable::lock_file_with_progress(path, callback)` | Same call, now returning `RegularFileLockError` instead of `io::Error` |

Required no-follow reads preserve the existing `read_file_no_follow` contract:
final symlinks fail with the operating system's open error, while opened special
files produce `ArtifactError::NotRegularFile`. Optional reads first reject a
non-regular directory entry, including a dangling symlink, with
`ArtifactError::NotRegularFile`. Only an initially missing pathname returns
`Ok(None)`; disappearance after the initial observation remains an error.
Both use the same no-follow open flags and bounded descriptor/stream reader.

Map old `NotRegular` handling to `ArtifactError::NotRegularFile`, and old
`TooLarge` handling to `ArtifactError::LimitExceeded { limit }`. Match native
failures through `ArtifactError::Io(source)`; allocation failures remain typed.
Do not treat every error as a cache miss or silently choose an effectively
unbounded budget. Existing `read_file` and `hash_file` still follow links;
`read_opened_file` still consumes the caller's descriptor at its current offset.
These APIs have distinct admission contracts and are not interchangeable.

Private reads still require a no-follow regular descriptor, permission bits
`0o600`, exactly one link and exactly `N` bytes, with a trailing read to reject
growth. `Ok(None)` now means missing; `Err` retains a read, permissions,
link-count or length failure. An error must not trigger key regeneration or
replacement. A caller that deliberately disables an optional feature for every
read failure may explicitly map the error to its existing product failure:

```rust,ignore
let key = read_private_bytes::<32>(&path)
    .map_err(|_| CaptureFailure::LocalKeyUnavailable)?
    .ok_or(CaptureFailure::LocalKeyUnavailable)?;
```

Lock creation, exclusion, one-second progress reporting and descriptor lifetime
are unchanged. Callback I/O errors are retained inside `RegularFileLockError::Io`.
The error implements `Display` and `Error::source`, so callers may preserve its
typed cause when projecting to their own error type. Both `ArtifactError` and
`RegularFileLockError` implement conversion into `io::Error`: native `Io(source)`
is returned unchanged, while other variants remain typed causes inside
`io::Error::other`. At existing `io::Result` boundaries use `.into()` or
`.map_err(io::Error::from)` instead of rebuilding a variant match or formatting
the error into text. Keep these projections at actual product boundaries rather
than recreating generic readers or lock wrappers in each consumer.

### Publication provenance

Upload now prepares archives without uploading, checks each recorded source and
package path, and verifies exact commit retrieval from the declared repository.
Failed or mismatched provenance prevents dispatch. The dirty-source dry run
remains separate. See [the publication procedure](../publishing.md) and
[#7](https://github.com/dragginzgame/ic-host-tooling/issues/7).

### Adoption evidence

The sibling source scan identified Canic as the consumer of the retired APIs,
including release-set persistence, build records, private diagnostic keys and
operation locks. Several release/protocol documents currently have no read
budget. An isolated migration qualifies the Host/CLI graph and selected runtime
paths on Linux; its proposed budgets still require consumer review before
adoption. Source identities, results and limitations are recorded in the
[current handoff](../status/current.md). Other inspected sibling
sources did not reference these retired APIs; that does not establish their
complete dependency or deployment state. Coordination remains on
[Canic #458](https://github.com/dragginzgame/canic/issues/458).

No sibling source or registry selection was changed by this library cleanup.
Following paths, no-follow paths and opened descriptors retain distinct trust
boundaries. Root confinement, ownership checks, concurrent writers, network
policy and recovery decisions remain caller-owned.
